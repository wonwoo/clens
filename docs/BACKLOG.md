# Backlog

Deferred work for clens, with the decision behind each item.

## Decided for now

- **Store conversation text only** (2026-09-26). The index keeps user messages and assistant replies. It does not keep tool outputs (command results, file contents read) or a copy of the raw transcripts, so once Claude Code deletes a transcript, its tool outputs are gone. Codex also rewrites old rollout files, and a message it drops from a file is dropped from the index on the next re-read. Revisit if a real lookup needs either. To revisit for tool outputs now (2026-09-28): context-mode, which kept command outputs searchable in its own store, is turned off, so nothing keeps past tool outputs searchable. The outputs are in the transcripts and the parser already reads them, keeping only their length (`tool_call.result_chars`): the 20,182 calls with a length total 42.2M characters, against 55.7M for all stored conversation text. Narrower than every output: Bash outputs only, failed calls only, or the first and last few KB of each. Secrets show up in outputs more often than in messages. Sessions whose transcripts are gone cannot get theirs back.
- **Skip the parent's history a Codex subagent rollout starts with, even where it is the only record** (2026-09-28). Newer Codex marks the copy (the parent's session_meta, up to `subagent_history_start_ordinal`); in older rollouts it is the turns whose ids are older than the thread. The parent's rollout holds those lines, so indexing the copy showed parent messages twice in search (1,604 rows in 61 older rollouts). Where the parent's rollout is incomplete, the copy is the only record and is lost with it: 7 messages of one conversation whose rollout stops after 4 lines, and a few tool calls in newer rollouts. Keeping a copy only when the parent lacks it would make one file's rows depend on another file, which Gate 2 rules out.
- **A recap goes through `/clens-recap`, invoked by the user** (2026-09-28). Asked "what did I do recently" at the start of a session, the agent called `clens_left_off` on its own but did not load the skill, so the answer missed other branches' commits, the middle of a long session and a stash. Pointing the server instructions or the tool description at the skill would only raise the odds of the agent choosing it; the user runs the skill instead.
- **`clens_session` gets no byte cap; its size is left to `limit`** (2026-09-28). It returns whole messages with no byte limit, unlike `clens_search` (8 KB) and `clens_recent` (32 KB). Measured over 38 real calls: median 3,921 characters, 7 above 8,192, maximum 15,966. Of those 7, four were many 1,500 to 2,400-character assistant replies stacked up by a large `limit`, two were dominated by teammate messages of 4,000 to 5,000 characters stored as `user`, and one by a pasted list. The agent already controls size with `limit`; a byte cap would mostly hide messages. Re-measured 2026-09-30 by replaying 88 past calls against the current index: mean 5,289 characters, maximum about 16,000, and 32 of their 1,281 messages over 2,000 characters. Cutting every message at 1,000 characters would save 22% (8% at 2,000), at the cost of the long replies that hold decisions. A single message is bounded since 2026-10-01: one over 20,000 characters keeps 5,000 at each end unless the call passes `full: true` (`src/mcp/session.ts`). No stored assistant reply is that long; the 288 messages over it are pasted logs, compaction summaries and long prompts. The call around the 163,548-character pasted log went from 330,777 characters to 23,801.
- **Large tool outputs are cut by the host's own settings, not by a clens hook** (2026-09-30). Measured over the index: outputs over 10,000 characters were 7% of calls and 51% of all tool output characters, most of it Codex. A PreToolUse hook blocking command shapes that were heavy in a project's history caught 1.3 to 7% of the characters above 10,000 in the later half of that history, while 74 to 82% of the calls it blocked had small output. Cutting the output instead is built in: Claude Code's `bashOutputMaxChars` in settings.json (default 30,000, 4,000 to 128,000; the rest goes to a file and the model gets a preview and the path, seen in the 2.1.285 binary, not run), and Codex's `tool_output_token_limit` in config.toml (keeps the head and tail; run with 2,500 on 0.155.1, the full output stayed in the rollout's `CommandExecution` item). Cutting outputs over 10,000 characters to 2,000 at each end would take 37% off what the model receives, before the cost of fetching a cut middle again. What clens could add: give back the middle Codex cut, from the rollout, if agents keep re-running commands to see it.
- **Pipeline and exec session text stays in the FTS tables** (2026-09-30). Taking it out would save about 70 MB once the tables are optimized, but it changes ranking although search already leaves those sessions out: on a copy, 245 of 460 replayed `clens_search` queries kept the same order and 324 the same set, since bm25's statistics change when rows leave the index.

## Known limits

- **Codex runs no SessionStart hook after compacting a subagent** (2026-09-29, Codex 0.155.1). After a compaction Codex queues a `compact` SessionStart (`core/src/session/mod.rs:3975`), but for a subagent session its hook runner returns without running it (`core/src/hook_runtime.rs:147`), so no record can be put back into a Codex subagent after its compaction. Root sessions get it.
- **A Codex hook runs only after the user trusts it** (2026-09-29, Codex hooks docs). A hook that is not managed by policy is skipped until the user reviews and trusts it with `/hooks` in Codex, and again after its definition changes; clens cannot do this for the user.

## Later

- **Semantic (embedding) search** (2026-09-26). Search is keyword-only: FTS5 word match, trigram substring match, and the ko/ja/zh morpheme layers. A query worded differently from the message misses it. Add embeddings once keyword search has proven itself in daily use, not before: it brings a model, a larger index and a rebuild path.
- **Synonyms and spelling variants in the query**, e.g. `cacheTimeout` / `cache timeout`, or an English term against its Korean one. Today the agent retries by hand, as the server instructions tell it to.
- **Mask secrets in stored text** (tokens, passwords pasted into messages). Needs a decision on what to mask and whether an unmasked copy is kept.
- **Ranking beyond noise removal**: judge transcripts and non-conversation rows are left out of search (2026-09-26). Recency or role weighting showed no gain on real usage (42 search-then-open pairs, too few to tune on); revisit with a labeled query set.
- **Check that agents reach for clens unprompted.** The server instructions now reach the agent whole (under Claude Code's 2,048-character cap). Seen once so far (2026-09-28): a new session asked about recent work called `clens_left_off` first, without being told to. One observation, not yet a measured rate.
- **Whether the compact hook adds anything to the summary** (2026-09-28). After a compaction the agent has Claude Code's summary, and can call clens itself when the summary lacks something: in the session that built `hooks/compact.mjs`, the summary left out how the hook had been built, and the agent found it with `clens_search`. The hook helps only when the summary drops something the agent does not know is missing. How often that happens is not measured; watch it in daily use.
- **clens's own token cost** (2026-09-30). clens tool outputs total 773,521 characters over the index, 0.45% of the 173.5M characters of all tool output; the large spend is shell output, not clens. What clens adds to every session: the server instructions (2,042 characters, just under Claude Code's 2,048 cap), which are what make agents reach for clens, so they stay as they are; and, where the skills are linked, their frontmatter in Claude Code's skill list (clens-recap 875, clens-stats 1,233 characters). clens-stats states the numbers-versus-conversation split in both `description` and `when_to_use`; shortening it needs a check that the skill still triggers. The tool definitions total 11,086 characters (clens_search 3,950, its input schema of 2,111 longer than its description of 1,839); Claude Code defers them until a tool is used, and whether Codex sends them with every request is not checked. After a compaction the hook adds at most 9,000 characters (about 5,400 in the session measured).
- **What the hourly FTS optimize leaves open** (2026-09-30). The driver now optimizes the FTS tables at most once an hour, and at the end of every rebuild (`optimizeFtsIfDue`, `src/indexer/driver.ts`); on the real index the first one, then a VACUUM by hand, took the file from 2.24 GB to 0.86 GB. Still to check: (1) nothing VACUUMs, so the file keeps the largest size it has reached; a version-mismatch rebuild deletes and re-inserts every row, so the FTS tables nearly double before the optimize at its end, and the file keeps that size (after the v11 rebuild: 1.12 GB, 240 MB of it free pages); (2) whether the WAL file stays at the size of an optimize's write (the FTS tables are about 200 MB); (3) that the file holds steady over hours of normal indexing: compare `PRAGMA freelist_count` and the `user_text_fts%_data` sizes a few hours apart. Not worth doing, from the same measurements on a copy: making the morpheme tables contentless (63 MB), trigram with `detail=none` (the trigram data is 167 MB after an optimize, and the layer would lose its rank), `event.source_file` as a number (its index is 63 MB).
- **A fork subagent's copy of the call that started it** (2026-10-01). Copies with the same uuid in two sessions (a resumed conversation) count once outside a single session (`notCopiedClause` in `src/analyzer/scope.ts`). A fork subagent's transcript also holds the parent's `Agent` call that started it, but under a new uuid, so that copy is still counted: 5 calls in the index.
- **Code provenance: from a line or a commit to the conversation that wrote it** (2026-09-30, spike in the session of that day). Buildable (`git blame` for line to commit, the commit subject inside a recorded `git commit` command for commit to session, edit text for uncommitted lines), but not worth a tool now: `clens_search` already puts the origin session in its top 10 for 43 of 60 sampled lines and commits, and of 19 past "why is this code like this" questions, 3 were about code from an earlier session. The part that pays: exact commit-to-session matching for `/clens-recap`, which attaches commits by time span; where two sessions' spans hold a commit (clens 13%, shop-service 28%, search-service 52% of the user's commits), the subject match picked one session in 21 of 21, 39 of 85 and 8 of 12. Cases it misses: `git revert --no-edit`, `commit --amend --no-edit` and `rebase` commits (the command holds no subject), a rebased or cherry-picked commit's committer time (use author time), files not yet added (blame fails), and a session started in another directory that ran `cd <repo> && git commit`.
- **Tell a new session the errors that keep coming back in its project** (2026-09-30). Of 557 failed calls with an error line (test failures left out), 153 (27.5%) repeated an error an earlier session of the same project had hit: a missing tool (`gh`, `pdftotext`), a Codex sandbox refusal, a wrong path guessed the same way (`sed: core/…: No such file` repeated 14 times in shop-service). It needs an error line stored per failed call (tool outputs are not stored today) and a SessionStart hook; the gain is small, under 1% of all calls.
- **Session record segments too large for two lines** (2026-10-05). A session record splits the conversation at compactions and at pauses over 2 hours and shows each segment's first request and last reply (`segmentsOf`, `src/mcp/left_off.ts`). A session that runs all day without either makes one segment of a hundred requests or more (216, 158 and 108 in one session of another project), and its first request and last reply are often about different things, so the middle of the work is hidden again, inside the segment. Counted by hand over 63 segments of six long sessions, before that day's fixes for `/compact` segments and Claude Code notices: 41% said what was done and where it stood, 46% answered the last question without saying what the segment did (most of a Q&A-style debugging session's), 13% said nothing. Not tried: a shorter pause once a segment passes some number of requests, a cut where the edited files change, or a few replies from inside a large segment. Each makes the record longer, and the compaction hook cuts it at 9,000 characters; segments come last so they are cut first.
- **Japanese and Chinese are installed for everyone** (2026-09-30; first raised 2026-07-04 and put off by the user). Korean is opt-in: its 84 MB model comes only with `clens install ko`. Japanese and Chinese are not: `lindera-wasm-nodejs-ipadic` and `lindera-wasm-nodejs-cc-cedict` are plain `dependencies` (`package.json:26-27`), their dictionaries are built into the wasm (13.1 MB and 9.5 MB), so every `npm install` downloads them and every process loads them at startup, whether or not the user writes Japanese or Chinese. `kiwi-nlp` itself (3.8 MB) is a plain dependency too. The loader already treats a missing package as "not installed" (`tryLoadJapanese` / `tryLoadChinese` in `src/indexer/lang/init.ts`), so what is left is the packaging: `optionalDependencies` still installs them by default (only `--omit=optional` skips them); a companion package, or a `clens install ja|zh` that installs the package like `clens install ko` fetches the model, makes them opt-in like Korean.
