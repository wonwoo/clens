# Backlog

Deferred work for clens, with the decision behind each item.

## Decided for now

- **Store conversation text only** (2026-09-26). The index keeps user messages and assistant replies. It does not keep tool outputs (command results, file contents read) or a copy of the raw transcripts, so once Claude Code deletes a transcript, its tool outputs are gone. Codex also rewrites old rollout files, and a message it drops from a file is dropped from the index on the next re-read. The one exception, since 2026-10-20: a failed call keeps the first 100 and last 200 characters of its output (`tool_call.error_excerpt`, `errorExcerpt` in `src/indexer/claude_parser.ts`), shown under the call in a session record and not searched. Revisit if a real lookup needs more.
- **Skip the parent's history a Codex subagent rollout starts with, even where it is the only record** (2026-09-28). Newer Codex marks the copy (the parent's session_meta, up to `subagent_history_start_ordinal`); in older rollouts it is the turns whose ids are older than the thread. The parent's rollout holds those lines, so indexing the copy showed parent messages twice in search (1,604 rows in 61 older rollouts). Where the parent's rollout is incomplete, the copy is the only record and is lost with it: 7 messages of one conversation whose rollout stops after 4 lines, and a few tool calls in newer rollouts. Keeping a copy only when the parent lacks it would make one file's rows depend on another file, which Gate 2 rules out.
- **`clens_session` gets no byte cap; its size is left to `limit`** (2026-09-28). It returns whole messages with no byte limit, unlike `clens_search` (8 KB) and `clens_recent` (32 KB). Measured over 38 real calls: median 3,921 characters, 7 above 8,192, maximum 15,966. Of those 7, four were many 1,500 to 2,400-character assistant replies stacked up by a large `limit`, two were dominated by teammate messages of 4,000 to 5,000 characters stored as `user`, and one by a pasted list. The agent already controls size with `limit`; a byte cap would mostly hide messages. Re-measured 2026-09-30 by replaying 88 past calls against the current index: mean 5,289 characters, maximum about 16,000, and 32 of their 1,281 messages over 2,000 characters. Cutting every message at 1,000 characters would save 22% (8% at 2,000), at the cost of the long replies that hold decisions. A single message is bounded since 2026-10-01: one over 20,000 characters keeps 5,000 at each end unless the call passes `full: true` (`src/mcp/session.ts`). No stored assistant reply is that long; the 288 messages over it are pasted logs, compaction summaries and long prompts. The call around the 163,548-character pasted log went from 330,777 characters to 23,801.
- **Large tool outputs are cut by the host's own settings, not by a clens hook** (2026-09-30). Measured over the index: outputs over 10,000 characters were 7% of calls and 51% of all tool output characters, most of it Codex. A PreToolUse hook blocking command shapes that were heavy in a project's history caught 1.3 to 7% of the characters above 10,000 in the later half of that history, while 74 to 82% of the calls it blocked had small output. Cutting the output instead is built in: Claude Code's `bashOutputMaxChars` in settings.json (default 30,000, 4,000 to 128,000; the rest goes to a file and the model gets a preview and the path, seen in the 2.1.285 binary, not run), and Codex's `tool_output_token_limit` in config.toml (keeps the head and tail; run with 2,500 on 0.155.1, the full output stayed in the rollout's `CommandExecution` item). Cutting outputs over 10,000 characters to 2,000 at each end would take 37% off what the model receives, before the cost of fetching a cut middle again. What clens could add: give back the middle Codex cut, from the rollout, if agents keep re-running commands to see it.
- **Pipeline and exec session text stays in the FTS tables** (2026-09-30). Taking it out would save about 70 MB once the tables are optimized, but it changes ranking although search already leaves those sessions out: on a copy, 245 of 460 replayed `clens_search` queries kept the same order and 324 the same set, since bm25's statistics change when rows leave the index.
- **Agents reach for clens unprompted** (2026-11-04). Measured over the index from 2026-10-01: in interactive sessions, 331 of 8,471 user turns called a clens tool, 309 of them with no mention of clens in the user's message. Of about 40 turns that pointed at earlier work ("어제", "저번", "예전에", "지난번"), every one whose answer lived in another session called clens; the ones that did not had the answer in the conversation, its compaction summary or a file. The word filter misses turns that point at earlier work without those words. Codex had 264 user turns and one such turn in the same span, too few to judge; measure it again once Codex use grows.
- **The compact hook adds what the summary leaves out** (2026-11-04). The hook's output is not indexed, so this was measured from the transcripts: it ran in 44 of the 45 transcripts with a compaction, 94 compactions in all. In 70 the record named edited files the summary did not. In 16 the agent used such a name in a reply or tool call before any tool output or user message showed it, about 12 leaving out guessable names such as `README.md` or `package.json`; one opened `ArgoKeywordForm.js` in another repository right after a compaction. Details the record lacks the agent fetches itself: 25 of the 79 compactions since 2026-10-02 were followed by clens calls on the current session, mostly when the user asked about something said before the compaction. Using a name only the record held is a proxy; it does not show the reply would have been worse without the hook.

## Known limits

- **Codex runs no SessionStart hook after compacting a subagent** (2026-09-29, Codex 0.155.1). After a compaction Codex queues a `compact` SessionStart (`core/src/session/mod.rs:3975`), but for a subagent session its hook runner returns without running it (`core/src/hook_runtime.rs:147`), so no record can be put back into a Codex subagent after its compaction. Root sessions get it.
- **A Codex hook runs only after the user trusts it** (2026-09-29, Codex hooks docs). A hook that is not managed by policy is skipped until the user reviews and trusts it with `/hooks` in Codex, and again after its definition changes; clens cannot do this for the user.

## Later

- **Synonyms and spelling variants in the query**, e.g. `cacheTimeout` / `cache timeout`, or an English term against its Korean one. Today the agent retries by hand, as the server instructions tell it to.
- **Ranking beyond noise removal**: judge transcripts and non-conversation rows are left out of search (2026-09-26). Recency or role weighting showed no gain on real usage (42 search-then-open pairs, too few to tune on); revisit with a labeled query set.
- **What the hourly FTS optimize leaves open** (2026-09-30). The driver now optimizes the FTS tables at most once an hour, and at the end of every rebuild (`optimizeFtsIfDue`, `src/indexer/driver.ts`); on the real index the first one, then a VACUUM by hand, took the file from 2.24 GB to 0.86 GB. Since 2026-11-05 an optimize VACUUMs the file when 100 MB or more of it is free pages, then checkpoints the WAL with TRUNCATE, waiting 5 s at most for open reads (`vacuumIfLoose`). After the v18 rebuild that took the file from 1.48 GB to 1.27 GB in 4 s on a copy; with another connection holding a read open the VACUUM took 13 s and the checkpoint gave up, leaving the 1.28 GB WAL for the next optimize. Still to check: that the file holds steady over hours of normal indexing: compare `PRAGMA freelist_count` and the `user_text_fts%_data` sizes a few hours apart. Not worth doing, from the same measurements on a copy: making the morpheme tables contentless (63 MB), trigram with `detail=none` (the trigram data is 167 MB after an optimize, and the layer would lose its rank), `event.source_file` as a number (its index is 63 MB).
- **The index grows without bound** (2026-11-04). Nothing is ever dropped, so the file grows with use: about 250 MB a month at October's rate (the event table and its five indexes about 160 MB, text and the three FTS layers about 65 MB, tool calls about 30 MB), some 3 GB a year; 1.35 GB on 2026-11-04, 193 MB of it free pages left by the v16 rebuild. One way looked at, not taken while other ways are considered: write no event row for a Claude Code `attachment` line that yields no other row. They are 330,000 of 777,000 events (42%), about 215 MB of the event table and its indexes, 70 to 80 MB of a month's growth. What depends on them: the 1,303 that own a Stop hook block or a message the user queued mid-turn must stay, since `notCopiedClause` (`src/analyzer/scope.ts`) tells a resumed copy by its event; `timeline.ts` measures time from event gaps, and dropping them changed it by under 1% (3,287 to 3,268 hours since 2026-10-01); `session.started_at/ended_at` come from every parsed line (`driver.ts`) and stay if the rows are dropped at write time, while the project and global spans of `clens_stats` read the event table and would start later in 2,755 sessions; `parent_uuid` is never read and turn numbers count only user and assistant rows. It needs a `SCHEMA_VERSION` bump, leaves the rows of sessions whose transcripts are gone, and gives no space back without a VACUUM. `system` lines (44,000, 6%) could go the same way, keeping the compaction boundary.
- **Where a session record segment stopped** (2026-10-05). A segment shows its first request, a `Topics:` line, a `Last change` line and its last reply (`segmentsOf` and `lastChange`, `src/mcp/left_off.ts`; how they were judged is in `docs/segment-eval.md`). Where the work stood is still unclear in 8 of the 40 segments of the evaluation set and 6 of the 20 of its second set, most of them questions and answers with no edit or commit. Since 2026-11-04 a session of one segment shows its `Last change` under its last reply too: a `/clens:continue` on 2026-10-29 took a session's side questions for its work, because the session was one segment and the record left out the Kafka commit those questions followed. Not tried: a cut where the edited files change, or a few replies from inside a large segment.
